# EC・自社LP価格改定

## Bridge Input Contract

- Run only from a fresh, non-resumed `codex exec`. Never open, read, search, or reuse app Chats, prior tasks or threads, transcripts, rollouts, or saved sessions.
- Treat the compact Bridge job input as complete. Use only that input and the references explicitly required by this Skill.

価格だけでなく、対象商品の同一性、各モール固有の公開操作、自社LPの本番表示まで確認する。

## 必ず読む資料

- ECを変更するときは [references/site-playbooks.md](references/site-playbooks.md) を読む。
- LPも変更するときは [references/lp-workflow.md](references/lp-workflow.md) を読む。
- 既知のチャーシュー商品なら [references/verified-products.md](references/verified-products.md) も読み、識別子を手掛かりにする。識別子だけで決めず、現行の商品名・容量・保存方法も照合する。

## 1. 改定条件を固定する

作業前に次を短く記録する。

- 商品の種類、形態、保存方法、容量
- 旧価格、新価格、差額 `新価格 - 旧価格`
- 対象チャネル
- TSAレシピの `product_lp_url`。URLがあればユーザーが毎回「LPも」と書かなくても必須更新対象にする。URLが空の時だけLPを対象外にする

ユーザーが「前回と同じ」「各サイト」「も」と指定した場合、既定対象を Amazon、楽天、Yahoo、メルカリShops、BASE、Qoo10、TikTokショップ、TSAレシピに登録された商品LPとする。

## 2. 対象商品を照合する

各サイトで商品名、販売個数、味、冷凍・常温、カット済み・訳ありなどの形態を照合する。可能なら ASIN、SKU、JAN、商品管理番号、商品番号も記録する。

類似商品が複数ある場合は価格を触る前に識別する。商品名の一部一致だけで選ばない。

TSAレシピの `fillingQuantity` は製造時の充填目標で、ECの商品説明に記載する内容量・正味重量と一致しない場合がある。確定識別子、または学習済み完全商品名と味・販売個数・形態・保存方法が一致して同一販売単位を一意に証明できる場合、充填目標と表示重量の数値差だけを理由に停止しない。差は `unit_evidence` に記録する。味、形態、販売個数、保存方法が異なる場合や候補が複数残る場合は従来どおりブロックする。

## 3. EC価格を変更する

目的別コネクター/APIがないことを確認してから、ログイン状態が必要なら `chrome:control-chrome` を使う。

### Chromeタブの安全ルール

1. EC作業を始める前に、ユーザーが現在開いているChromeタブを一度だけ一覧取得する。
2. 各ECは、その公式販売管理サイトですでにログイン済みの既存タブを優先して取得・再利用する。
3. 同一ECの既存タブが複数ある場合、最初の候補が「別のブラウザ作業で使用中」でも停止せず、同じ公式ホストの残りの候補を順に取得する。全候補を試すまで操作待ちにしない。
4. 全候補が別セッションで使用中、または対応タブがない場合は、選択済みの同じChromeプロファイル内に `chrome.tabs.new()` で対象EC専用の一時タブを1枚だけ作り、公式URLへ直接移動する。これは別ブラウザ・別プロファイルではなく、既存Chromeのログイン状態を共有する退避経路である。
5. `browser.tabs.new()`、`window.open()`、新規ウィンドウ、シークレットウィンドウ、一時プロファイル、別ブラウザは使用しない。一時タブは1フェーズにつき対象ECごとに最大1枚とする。
6. ユーザーが用意した既存タブを閉じたり、破棄したり、別タブへ置き換えたりしない。通常のECタブを引継ぎ・成果物として保持せず、処理終了時に取得状態を解放する。Bridgeが作った一時タブだけは最終確認後に閉じる。
7. サイトは一つずつ処理する。全サイトを同時に開かず、全画面DOMを取得しない。検索結果の対象行、識別子、販売価格、販売単位、送料条件、保存操作だけを狭く読む。

### タブ解放と競合判定

- 取得した既存タブとBridge作成の一時タブは別配列で管理する。既存タブには成功・失敗・操作待ちのどの終了経路でも `markHandoff()`、`markDeliverable()`、`close()` を呼ばない。一時タブだけを最終確認後に閉じ、速やかに結果を返して未マークの既存タブを解放する。
- Chromeのturn終了通知に必要なrolloutを残すため、CLIの `--ephemeral` は使用しない。保存されたrolloutを後続ジョブの入力や再開元には使わない。
- 既存タブの取得時に `another browser session`、`別のブラウザ作業セッションで使用中` などが返ってもログイン切れではない。Chrome上部の存在不明な操作を案内せず、同じChromeの一時タブへ自動退避する。
- 「ログインしてください」と案内できるのは、取得に成功した既存タブまたは同じChromeの一時タブ上で、実際の公式ログイン・認証画面を確認した場合だけとする。

### TSA Bridgeの実行承認

- TSAの価格反映画面は、管理者へ対象商品・対象EC・税込目標価格を示す確認ダイアログを出し、承認後だけジョブを登録する。一括予約は「予約分をまとめて実行」を確認した時点で実行承認を記録する。
- `TASK_JSON.operatorAuthorization.executionAuthorized=true` で、商品ID・対象EC・目標価格が同じ場合、その記録を当該ジョブの正式なユーザー承認として扱う。Bridgeにはチャット返信経路がないため、保存直前に「保存を実行と返信」「続行を確認」などの二重確認を要求してはならない。
- 商品識別、保存済み現価格、絶対目標価格が検証済み計画と一致したら、対象サイトの保存・送信・更新を実行し、再読込で保存値を確認する。`waiting_for_user` はログイン、MFA、CAPTCHA、アカウント選択、ブラウザ権限、または新しい判断材料が必要な曖昧状態に限定する。
- 前回停止時の未保存入力がタブに残る場合がある。各サイトの現価格確認前に対象編集画面を再読込または再遷移し、未保存DOM値を破棄してからサーバー保存値を読む。
- `TASK_JSON.productMappings` がある場合は、TSAの売上取込で当該商品へ学習済みのEC別商品名である。商品名、容量、保存方法、形態を照合しながら、各ECへ渡された全候補を検索してからだけ `対象商品なし` と判定できる。一般名やJANだけの検索で0件になっても終了しない。
- `TASK_JSON.verifiedProductIdentifiers` があるサイトは、TSAで当該JANに確定登録済みのASIN・SKU・商品管理番号・商品コード・商品ID・商品番号を先に使う。確定識別子を公式画面で解決できない時は `対象商品なし` ではなく、そのサイトをブロックとして証拠を残す。
- 公式管理画面で十分に検索し、学習済み候補とも一致しないことを証拠付きで確認できたECは `対象商品なし` として処理対象外にできる。その判定は他ECや商品LPの反映を止めない。類似商品への置換は絶対に行わない。

### 全EC共通の制限付き自律復旧

- Amazon、楽天、Yahoo、メルカリShops、BASE、Qoo10、TikTokのUI・導線・必須項目が変わった場合、古いクリック手順を盲目的に繰り返さない。画面に出た正確なエラーと現在の保存状態を読み、計画済みの商品・サイト・目標価格を保ったまま、価格変更に必要な最小の修復を自律的に選ぶ。
- 新しく必須になった項目を変更できるのは、対象商品の正確な値がこのSkill、`verified-products.md`、TSAの商品紐付け・商品LP、または公式管理画面の現在の保存値で明示的に証明できる場合だけとする。価格以外を修復した場合は、変更した項目と根拠を結果へ記録する。値を証明できなければ推測せず、そのECだけをブロック状態で停止する。
- 同じECの同じ修復・保存経路は最大2回まで試行する。同じエラーが残る、別の未確認項目を要求される、または下記禁止事項へ触れる場合は、それ以上試さず正確な証拠を残して停止する。

#### 自律復旧の絶対禁止事項

- 別商品、別ASIN、別SKU、別JAN、別容量、別保存方法、別アカウント、別店舗へ切り替えない。
- 検証済み計画と異なる価格を設定・保存しない。
- 在庫、出荷方法、配送、税、商品名、画像、説明、バリエーション、販売単位、その他の商品属性は、その項目と正確な値が当該商品の復旧に必要だと決定的に証明できない限り変更しない。
- 未確認値を推測しない。ログイン、MFA、CAPTCHA、アカウント選択、権限確認を回避しない。一括変更を使わない。
- ログイン、MFA、CAPTCHA、アカウント選択、権限画面は1回確認した時点で停止する。再読込、再ログイン、別経路探索を反復せず、直ちに `waiting_for_user` を返す。
- 別ブラウザ、別プロファイル、別ウィンドウを使わない。ユーザー所有の既存タブを閉じない。

- BASE以外は原則として新価格をそのまま設定する。
- BASEの通常商品は、対象商品が実在しユーザーが明示した場合だけ変更する。
- TikTokショップがBASE連携なら TikTok Seller Centerを編集せず、BASE内の `【TikTok連携】` 商品を変更する。
- BASE通常商品など送料別の商品は `BASEの新価格 = BASEの現価格 + 改定差額` とする。`【TikTok連携】【送料無料】` など送料無料の商品は他の送料無料モールと同じ新価格にする。商品名だけで決めず、各商品の送料設定を確認する。
- 対象が存在しなければ類似商品を代用せず、「登録なし」と記録する。

保存後は一覧または再読込でサーバー側の価格を確認する。単に入力欄へ数字が入った状態を完了扱いしない。

価格改定後は各公開商品ページの文言も確認し、商品名、容量、冷凍・常温、カット済み・訳あり、原産地が対象商品と一致していることを確認する。既知商品の標準表記は `references/verified-products.md` を正とする。

## 4. 自社LPを必ず変更する

TSAレシピに商品LP URLがある場合は、ECとは独立した必須工程として必ず処理する。ECとLPは1件ずつ順番に計画・書込・再読込確認し、ある工程がブロックしても、すでに成功した工程を無効化せず、残りの工程へ進む。最後に `blocked`、`submitted_pending`、結果欠落、未完了LPだけを再実行対象にする。

LPの編集元、対象商品、旧価格、変更箇所、目標価格を確定できない場合はLP工程だけをブロックし、類似ページを代用しない。EC成功結果を取り消したり、同じECを最初から再実行したりしない。ただし、TSAレシピの商品識別情報または保存価格が実行中に変わった場合は全体安全停止とする。

TSAの `https://v0-tsa-19.vercel.app/links` を正として、商品に一致するLPを探す。TSAのタイトルや説明が古い場合があるため、リンク先の現行商品内容も確認する。

検証済みFresh Clone内の計画対象箇所がすべて目標価格で、TSA登録済み公開URLでも対象商品と全目標価格を確認できる場合は、変更不要の反映済みとして扱う。AI書込・空コミット・不要な再デプロイは行わず、確認した現行コミット、公開URL、最終価格を証跡に残す。計画対象に旧価格が一か所でも残る場合はこの扱いにせず、そのLP工程だけを通常どおり編集・ビルド・push・デプロイ・公開確認する。

チャーシュー商品の価格改定では、専用LPに加えて複数商品LP `https://chasieu.aizu-syokubura.com/` も毎回確認する。対象商品のカード・価格表示だけを修正し、他のチャーシュー商品を一括置換しない。

ローカル編集元を探すときは次を実行できる。

```powershell
powershell -ExecutionPolicy Bypass -File scripts/find-lp-source.ps1 -LpUrl "https://example.com/" -FreshClone
```

既存ローカルクローンを最新版と見なしてはならない。ジョブごとにVercelの接続先GitHubから本番ブランチを新規クローンし、`HEAD` と `origin/<production_branch>` の一致を確認したものだけを編集元にする。価格表示、構造化データ、CTA付近の価格を検索し、同じ販売条件を示す箇所だけ変更する。

ビルド、既存の本番デプロイ経路、登録済み商品LP URLでの価格確認まで行う。Vercelが返す生成deployment URLと登録済み独自ドメインは異なってよい。生成URLは有効なHTTP(S) URLと公開コミットを確認し、最終価格は必ずTSA登録済み商品LP URLを直接再取得して確認する。公開URLで対象商品の全変更価格を確認できなければLPだけを未完了にする。詳細はLP資料に従う。

## 5. 完了判定と報告

サイトごとに次のいずれかを明記する。

- 反映済み
- 送信済み・審査/反映待ち
- 対象商品なし
- ブロック中

最終報告には、サイト、最終価格、商品識別子、公開操作の結果、LP URLを含める。Amazonなどが非同期なら、現在の一覧価格も併記して「反映済み」と誤記しない。

## 重要な安全策

- 別容量、別形態、国産品、カット済みと訳ありを取り違えない。
- Yahooは保存だけで終わらず反映管理まで行う。
- マスク入力では必ず入力後の正確な値を確認する。旧価格へ追記された巨大値を保存しない。
- 失敗や審査待ちを成功として報告しない。
- LPリポジトリが汚れていたら、無関係な変更をステージ・上書きしない。
- ブラウザ作業終了時もユーザーが用意した既存ECタブを閉じず、通常の取得状態を解放する。
